## 2. Root-cause reports

### 2.1 Premature automatic checkout — ROOT CAUSE

There were **two** independent client-side mechanisms that could check everyone
out early, both in `attendance-tracker/src/hooks/useAttendance.js`:

1. **A browser timer ran every 30 seconds** and, when the *device* clock passed
   `meetingEnd`, wrote a global force-checkout to Firestore. It used
   `isAfterSystemForceCheckoutTime(new Date(), meetingEnd)` — i.e. the **device's
   own clock and timezone** via `Date.setHours()`. A kiosk on Central time, a
   tablet with a wrong clock, or any non-Eastern device would trigger at the wrong
   absolute time.
2. **`meetingEnd` could be overridden by stale local settings.** The effective
   settings were `{...DEFAULT, ...Firestore, ...localUiPrefs}`, so a stale
   `tn170-kiosk-ui-prefs.meetingEnd` of `20:00` on a device produced an **8:00 PM**
   checkout — matching the reported incident. On failure the code even applied the
   checkout **locally** and reported success, masking the Firestore error.

The ~9:39 PM incident is consistent with either the delayed **server** cron
firing after 9:30 PM (acceptable) or a device-clock client run; both are removed
as risks by the fix below.

**Fix:** The browser can no longer perform a global force checkout at all. All
three hook variants had their 30-second force-checkout effect removed, and
`systemForceCheckoutFirestore()` was deleted. Local UI prefs can no longer
override the authoritative schedule (`meetingDay/meetingStart/meetingEnd` now come
only from Firestore settings or the built-in default `21:30`). The **only**
force-checkout is the trusted server-side GitHub Action at 9:30 PM Eastern.
Individual admin force check-out (one member) is unchanged.

### 2.2 Missing Discord report — ROOT CAUSE (two compounding causes)

1. **The scheduled workflows were skipping entirely.** GitHub delivered the
   Tuesday-night cron **1–3 hours late**, after midnight Eastern (Wed 00:25–01:17
   ET on Jul 14 & 21). The gates checked "is it currently Tuesday hour 22", which
   is **false on Wednesday**, so both workflows **skipped and reported success**.
   The weekly-email gate was even more brittle: it required an **exact** `hour==22`
   match, so anything but a perfectly on-time 02:00-UTC run failed the gate. Net
   result: no scheduled run has done real work in weeks.
2. **Discord was coupled to email.** `weekly-attendance-email.js` threw
   `EMAIL_RECIPIENTS is empty` *before* attempting Discord, and if email later
   failed but Discord succeeded (or vice-versa) the job status was misleading. A
   Resend "test-mode 403" (account can only email its own address until a domain is
   verified) would have blocked delivery under the old ordering.

The Discord **webhook itself works** — a manual June 20 run posted the ZIP
successfully. The problem was never the webhook; it was the schedule gate and the
email coupling.

**Fix:** Rewrote the report script so **Discord is delivered first and
independently** (missing/failed email never blocks it); moved delivery to **10:00
PM ET**; made the schedule gate **tolerant of multi-hour delay** (it targets the
correct Tuesday meeting date and still runs from a delayed Wednesday-morning cron);
added persistent **idempotency** (`automationRuns/report-<date>`) so duplicate runs
post **once**; added explicit HTTP handling (200/204/401/403/404/429-with-retry_after/5xx-backoff);
and made a required-Discord failure **fail the workflow visibly** and **upload the
report ZIP as a GitHub Actions artifact**.

### 2.3 Cross-device desync — ROOT CAUSE

Meetings were selected by a query on `meetingDate == today`, where "today" was the
**UTC** date (`new Date().toISOString()`). Meetings were created with **random**
document IDs. Two consequences:

- After ~8:00 PM EDT the UTC date rolls to the next day. A device opening at
  8:30 PM queried `meetingDate == <Wednesday-UTC>` and found **nothing** (or created
  a *second* meeting doc), so it did not see members checked in earlier that evening.
- `limit(1)` on the query picked an arbitrary doc when duplicates existed.

**Fix:** Meetings now use a **deterministic document ID equal to the Eastern
meeting date** (e.g. `meetings/2026-07-21`). Every device and the server resolve
the exact same document by ID (`subscribeToActiveMeeting` subscribes to the doc
directly; `ensureActiveMeeting` creates/updates it idempotently). The server
scripts read the same deterministic ID with a legacy `meetingDate`-query fallback,
so this is safe to deploy without a data migration.

### 2.4 Member creation failure — ROOT CAUSE

There were **two competing roster-management UIs**:

- `pages/AttendanceList.jsx` (`/admin/members`) called `createPendingMember()` and
  `updatePendingMemberCapid()`. In production (Spark kiosk mode) the hook does
  **not** expose those functions — they are `undefined` — so clicking "Create
  Pending" threw `TypeError: createPendingMember is not a function`.
- `components/MemberRosterManagement.jsx` (rendered on the Dashboard) uses the
  **working** `createMember`/`updateMember` path (`createMemberSpark`), which
  validates CAPID/name/grade, verifies the admin's PIN and `canManageMembers`,
  writes the member with the existing roster schema, and logs an activity event.

**Fix:** Removed the obsolete panel from `AttendanceList.jsx` and rendered the
single authoritative `MemberRosterManagement` component there instead, so
`/admin/members` and `/admin/dashboard` share **one** roster workflow. Extracted
the input validation into `data/memberValidation.js` and covered it with tests.

## 8. Recovering from a failed Discord delivery

1. Open the failed **Weekly attendance report** run → **Artifacts** → download
   `tn170-attendance-report` (the CSV is there even though delivery failed).
2. Read the `[discord] FAILED …` log line for the HTTP status:
   - 404 → webhook deleted/regenerated → recreate it (section 6A) and update the secret.
   - 403 → webhook points to the wrong channel or lacks permission → recreate in the
     correct channel.
   - 401 → invalid/rotated webhook → recreate.
   - 429/5xx → transient; just re-run.
3. Re-run: Actions → **Weekly attendance report** → `delivery_mode = discord_only`,
   `force_send = true`, `force_resend = true`. Idempotency ensures it posts **once**.

## 9. Rollback procedure

- **Everything:** revert the merge commit of this branch on `main`
  (`git revert -m 1 <merge-sha>`), or reset `main` to the pre-merge commit
  (`15199df`) and force-push if permitted. Then re-run `npm run build:pages` from the
  restored source and push so Pages matches.
- **Rules only:** `git checkout 15199df -- firestore.rules && firebase deploy --only
  firestore:rules`.
- **Workflows only:** revert the two files under `.github/workflows/` and push.
- **Frontend only:** restore the previous root `index.html`, `404.html`, `assets/`
  from `15199df` and push.
- The Firestore data model is backward compatible (new deterministic meeting IDs and
  the `automationRuns` collection are additive; legacy meetings still resolve via the
  fallback query), so no data migration or rollback is required.

## 10. Remaining risks & deferred work

- **Unauthenticated read exposure remains** (roster names, guest email/phone,
  crackable 4-digit PIN hashes). Rules cannot close this under a no-Auth public
  kiosk. The recommended containment — **Firebase App Check (reCAPTCHA v3, free) +
  enforcement on Firestore** — is scaffolded in code (set `VITE_RECAPTCHA_SITE_KEY`)
  but must be enabled in the console. The full fix is server-side PIN verification.
  See **docs/SECURITY.md** for the assessment, options, cost, and steps.
- **GitHub Actions delivery delay** can be hours. Mitigated by delay-tolerant gates,
  multiple crons, a Wednesday-morning safety net, and idempotency — but a meeting
  held on a **non-Tuesday** would need a manual `meeting_date` run.
- **Email to non-owner addresses** needs a verified Resend domain; until then email
  may 403 (harmless — Discord is unaffected).
- Client kiosk "force checkout due" hints are still device-time based (advisory only).
- Full multi-client Firestore sync is validated by the deterministic-ID design and
  the pre-Tuesday manual checklist; automated tests cover the pure sync/idempotency
  logic (the emulator is not part of this environment).
